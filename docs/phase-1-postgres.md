# Phase 1: PostgreSQL foundation — detailed plan

The overview is in [`PLAN.md`](../PLAN.md) › Phase 1; the tables are designed in
[`database-design.md`](database-design.md). This document is the working plan: what changes, in which files, in which
order, and how we know it's done.

## 1. Goal and definition of done

**Goal:** the app does exactly what it does today, but reads its data from PostgreSQL instead of the SQLite file, in
development, in tests and in the deployed app. No new features: accounts and orders start in Phase 2, on this
foundation.

**Done when:**
- [ ] Every page and every `/api` route answers the same as before (same status, same JSON); the contract test proves
      the API, the e2e suite proves the pages.
- [ ] Nothing imports `node:sqlite`; `.data/`, `servedFile`, `outputFileTracingIncludes` and the SQLite parts of
      `vercel.json` are gone.
- [ ] `npm run build` needs **no database** (nothing is pre-rendered from it).
- [ ] `npm run db:migrate`, `db:seed`, `db:check`, `db:reset` work against any Postgres given by `DATABASE_URL`.
- [ ] Integration tests run on PGlite with no Docker and no network; backend coverage stays at 100% of lines.
- [ ] A new developer can go from clone to running app following `farmart-onboard` and `/on-boarding`.
- [ ] The live demo still works (section 10).

## 2. Scope

**In:** the catalog tables (categories, products, product_details, deals, banners, settings) on Postgres via Drizzle;
the connection; migrations; the seed and its checks; the product page reading the database; tests, e2e and smoke on
Postgres; docs and skills.

**Out (later phases):** users, sessions, coupons, orders (Phase 2–3); TanStack Query and Zustand (Phase 2); the AWS
infrastructure (Phase 5). The new catalog columns that only the admin needs (`is_active`, `updated_at`) **are** added
now, so Phase 4 needs no catalog migration; nothing reads `is_active` except "hide inactive products" in the queries.

## 3. Constraint: the final hosting isn't decided yet

The target is AWS with RDS (PLAN.md › Decisions), either **A** (static frontend on S3/CloudFront + API on API Gateway/
Lambda) or **B** (the whole Next.js app on AWS with OpenNext). Phase 1 must not block either, so:

- **Plain Postgres only.** No Supabase-only features (Auth, Data API, Storage); nothing in code names a provider.
- **One configuration surface:** `DATABASE_URL`, plus `DATABASE_SSL` and `DATABASE_POOL_MAX` (section 6). RDS, RDS
  Proxy, Supabase and a local container then differ only in env vars.
- **All data access stays in `src/server/`**, behind the functions the route handlers already call. Under option A
  those same functions move behind API Gateway unchanged; under option B nothing moves.
- **The build reads no data** (section 9), which both options need: A builds static files, B builds Lambda bundles,
  and neither should connect to a database at build time.

## 4. Decisions for this phase

| # | Decision | Choice | Why |
|---|---|---|---|
| D1 | ORM / query builder | **Drizzle ORM** `drizzle-orm` 0.45, migrations with `drizzle-kit` 0.31 | Typed, SQL-first, plain SQL migration files in git |
| D2 | Driver | **postgres.js** (`postgres` 3.4) | Small, fast, works with every pooler (`prepare: false`) |
| D3 | How code gets the database | **Passed in**: `createCatalog(db)` returns the query functions; the app builds one instance from `getDb()` | Tests inject their own PGlite database without globals; option A can construct it inside a Lambda handler |
| D4 | Test database | **PGlite** `@electric-sql/pglite` 0.5, one fresh, migrated, seeded database per test file | No Docker or network; same migrations as production |
| D5 | e2e database | **PGlite over TCP** with `@electric-sql/pglite-socket` 0.2, started by Playwright's webServer, seeded first | `next start` needs a real connection; keeps e2e independent of any shared database (the reason e2e got its own database) |
| D6 | Local development database | **Docker Compose `postgres:17`** (`compose.yaml`, `npm run db:up`); any other Postgres works by changing `DATABASE_URL` | Same engine family as RDS; offline; one command |
| D7 | Rendering | Pages that read the database render **on request** (`export const dynamic = "force-dynamic"`); `generateStaticParams` and `revalidate` removed from them | The build needs no database (section 3); the catalog is small enough; caching is a separate, measured step later |
| D8 | Migrations | Generated by `drizzle-kit generate`, reviewed, committed in `drizzle/`; applied with `npm run db:migrate`, **never** from the build | Builds (and previews) must not change a database |
| D9 | Schema files | `src/server/db/schema/` split by area: `catalog.ts` now; `accounts.ts`, `orders.ts` later; `index.ts` re-exports | Keeps each phase's tables together |
| D10 | Interim deploy | The live demo moves to a hosted Postgres (Supabase free, using only plain Postgres) until AWS exists | Keeps the demo alive; changes nothing in code (section 10) |

D5 and D6 are the two to confirm (section 13).

## 6. The connection (`src/server/db/client.ts`)

```ts
export function createDb(url: string, { ssl, max }: { ssl?: "require" | false; max?: number } = {}) {
  const sql = postgres(url, { ssl, max: max ?? 3, prepare: false, idle_timeout: 20, connect_timeout: 10 });
  return drizzle(sql, { schema });
}
export type Db = ReturnType<typeof createDb>;   // tests use a PGlite-backed Drizzle instance of the same shape
```

- `getDb()` builds one instance per process from env vars and keeps it on `globalThis` (dev hot reload, warm Lambdas).
- `DATABASE_URL` (required at runtime), `DATABASE_SSL=require` (RDS, Supabase) or unset (local), `DATABASE_POOL_MAX`
  (default 3; serverless behind a pooler or RDS Proxy keeps it small).
- `prepare: false` keeps it compatible with transaction poolers (Supabase 6543, PgBouncer); RDS Proxy accepts it too.
- A missing `DATABASE_URL`, a refused connection, a missing table or an empty `products` table each become a
  `DatabaseNotReadyError` with the command that fixes it, as today (`npm run db:up`, `db:migrate`, `db:seed`).

## 7. Schema translation (catalog)

| SQLite today | Drizzle / Postgres | Note |
|---|---|---|
| `TEXT PRIMARY KEY` ids | `text().primaryKey()` | Ids unchanged (`bs5`, `fruits-vegetables`): URLs, spec, tests stay |
| `featured INTEGER CHECK IN (0,1)` | `boolean().notNull().default(false)` | |
| `price_cents INTEGER CHECK > 0` | `integer().notNull()` + `check()` | Same rules as CHECK constraints |
| `rating REAL` | `numeric({ precision: 2, scale: 1 })`, mapped to `number` | Avoids 4.299999 |
| `highlights TEXT` (JSON) | `text().array().notNull().default([])` | |
| `created_at TEXT` | `timestamp({ withTimezone: true })` | `starts_at`/`ends_at` on banners too |
| `placement TEXT CHECK IN (…)` | `pgEnum("banner_placement", […])` | |
| — | `products.is_active boolean default true`, `products.updated_at timestamptz` | For Phase 4 |
| `PRAGMA user_version` (`SCHEMA_VERSION`) | drizzle-kit's migrations table | `SCHEMA_VERSION` disappears; "outdated" becomes "not migrated" |

## 8. Porting the queries (`src/server/catalog.ts`)

- Every function becomes `async`; callers `await`. Pure helpers (`searchTerms`, `dealEndsAt`, `toProduct`, money
  conversion) stay synchronous and keep their unit tests.
- Keep the SQL shape: Drizzle's query builder for simple reads, `sql` templates where today's SQL is clearer (the
  search ranking). Values are always parameters; `ORDER BY` still comes from the whitelist.
- `LIKE … ESCAPE` → `ILIKE … ESCAPE` with the same `likeEscape`; `stripUnused` goes away (Drizzle builds only the
  conditions used).
- Booleans are real booleans (`featured = true`); times compare as `timestamptz` (`listBanners(now)`).
- Results must be byte-for-byte the same JSON: the contract test and the existing integration assertions are the
  safety net, so they are ported **before** the queries (section 12, step 1.3).

## 9. Pages and rendering

| Page | Today | Phase 1 |
|---|---|---|
| `/` | `revalidate = 60`, pre-rendered at build | `dynamic = "force-dynamic"`, `await catalog.*` |
| `/search` | dynamic | `await` the queries |
| `/products/[id]` | `generateStaticParams` from `src/data`, reads `src/data` | **reads the database** via `getProduct` (Workflow C); `generateStaticParams` removed; unknown id → `notFound()` |
| `/design/*` | static from `DESIGN.md` | unchanged (no database) |

e2e image baselines should not change (same data, same markup); if one does, look before re-approving.

## 10. Environments

| Where | Database | How |
|---|---|---|
| Local dev | Postgres 17 in Docker | `npm run db:up` (compose), then `db:migrate`, `db:seed`; `.env.local` has `DATABASE_URL=postgres://farmart:farmart@localhost:5432/farmart` |
| Integration tests | PGlite in process, per file | `setup-db.ts`: create → migrate (`drizzle-orm/pglite/migrator`) → seed |
| e2e | PGlite over TCP on port 5433 | Playwright webServer: `scripts/e2e-db.mjs` (migrate + seed) then `next start` with that `DATABASE_URL` |
| Smoke | the same e2e database for "healthy"; an unreachable URL for the failure mode | `scripts/smoke.mjs` |
| Live demo (interim) | Supabase free project, plain Postgres | `DATABASE_URL` (port 6543), `DATABASE_SSL=require` in Vercel; migrate and seed once by hand. Replaced by RDS in Phase 5 |

If Docker isn't available, `DATABASE_URL` can point at any Postgres 15+ (a cloud dev database, or PGlite via
`scripts/e2e-db.mjs` for a quick look).

## 11. Commands (`package.json`)

| Command | Does |
|---|---|
| `npm run db:up` / `db:down` | Start / stop the local Postgres container |
| `npm run db:generate` | `drizzle-kit generate`: new migration from schema changes |
| `npm run db:migrate` | Apply pending migrations to `DATABASE_MIGRATION_URL ?? DATABASE_URL` |
| `npm run db:seed` | Empty the catalog tables and load `src/data` (refuses a production-looking URL unless `--force`) |
| `npm run db:check` | Compare the database with `src/data`, read-only, list differences |
| `npm run db:reset` | Drop the schema, migrate, seed (local and test databases only) |

## 12. Work breakdown (each step is one PR, green on its own)

1. **1.1 Tooling.** Add the dependencies, `compose.yaml`, `drizzle.config.ts`, the `db:*` scripts, `.env.example`.
   No app change. *Exit:* `npm run db:up` gives a reachable Postgres.
2. **1.2 Schema + migrations.** `schema/catalog.ts`, the first generated migration and the hand-written extras;
   `mermaid.html` and `er-diagram.test.ts` checked against the Drizzle schema. *Exit:* migrations apply cleanly to
   local Postgres and to PGlite.
3. **1.3 Test harness.** `setup-db.ts` on PGlite (migrate + seed per file); the seed rewritten for Drizzle
   (`seed`, `reseed`, `compareWithSeed`) with its tests. *Exit:* seed tests green on PGlite.
4. **1.4 Queries.** `createCatalog(db)`, every function async on Drizzle; `catalog.test.ts`, `routes.test.ts`,
   `contract.test.ts` green unchanged in their assertions. *Exit:* `npm run test:backend` green, 100% lines.
5. **1.5 App wiring.** `client.ts`/`getDb()`, `status.ts`, route handlers and pages `await`; product page on the
   database; rendering per section 9; remove SQLite (`node:sqlite`, `servedFile`, `.data`, tracing includes).
   *Exit:* `npm run build` with no database, app works on local Postgres.
6. **1.6 e2e and smoke.** `scripts/e2e-db.mjs`, Playwright config, smoke modes. *Exit:* `npm run test:e2e` and
   `npm run smoke` green; no image baseline changed (or each change looked at).
7. **1.7 Docs and deploy.** `AGENTS.md`, `README.md`, skills (`farmart-onboard`, `farmart-backend-feature`,
   `farmart-verify`, `farmart-docs` map), `/on-boarding` (status and pipeline), `vercel.json`; interim database for the
   live demo. *Exit:* fresh-clone onboarding works in a scratch copy; live demo answers 200.

## 13. Open questions (defaults apply if no answer)

1. **D6: Docker on your machine?** If not, the default becomes a cloud dev database (Supabase free) for `npm run dev`.
2. **D5: PGlite over TCP for e2e**, or a Docker Postgres for e2e too (closer to production, needs Docker in CI)?
   Default: PGlite; switch if it proves flaky.
3. **D10: keep the live demo during Phase 1** (interim Supabase), or let it go stale until AWS? Default: keep it.
4. **Caching:** render on request with no cache for now (D7), or add Next's cache with tag invalidation right away?
   Default: no cache in Phase 1; measure first.

## 14. Risks

| Risk | Mitigation |
|---|---|
| PGlite behaves differently from server Postgres (single connection, extensions) | Phase 1 has no concurrency logic; a CI job with real Postgres comes before Phase 3's stock and coupon transactions |
| `pglite-socket` is young (0.2) | It's only the e2e database; fallback is Docker Postgres (D5) |
| JSON output changes subtly (numeric as string, dates as `Date`) | Map types explicitly in `toProduct`; contract and route tests assert exact JSON |
| Rendering on request is slower than the pre-rendered home page | Small catalog, indexed queries; measure with the smoke run; add caching later if needed |
| The async change breaks a caller nobody tested | `tsc` flags every un-awaited call that's used as a value; ESLint `no-floating-promises` on `src/server` |
